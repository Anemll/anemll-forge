Two engines, one model: a 27B LLM on the Neural Engine and the GPU of an M6 Mac

A plain-language tour of how we run Qwen3.8-27B on an M6 Mac with the Apple Neural Engine and the GPU working on the same model at the same time, and how a small "tree" trick makes it answer faster. The details, the measurements and everything that did not work are in the full article and the tree-verification paper.

1. Two engines in one chip

An M6 has two big accelerators that share the same memory. The Neural Engine (ANE) runs fixed, pre-compiled programs and is very efficient at large matrix multiplications. The GPU is flexible: you write your own kernels. Most local LLM apps pick one. We use both for one model, and they read one copy of the weights: the GPU reads the weights straight out of the Neural Engine's compiled programs, so the 27B model does not need twice the memory.

2. Reading the prompt: split the work

Each of the model's 64 layers has two halves: a mixer (attention or Gated DeltaNet, which looks across the tokens) and a feed-forward network (which works on each token alone). We put every feed-forward network on the Neural Engine and every mixer on the GPU, and keep both busy at once by passing blocks of tokens back and forth.

3. Writing the answer: guess, then check

Generating one token at a time is slow for a 27B model: every token reads all the weights. So we use speculative decoding. A small drafter model guesses the next 7 tokens, and the big model checks all of them in one call of 8 rows (the last confirmed token plus 7 guesses). Every guess that matches what the big model would have written is kept; the first wrong one ends that check, and the big model supplies the correct token there. The big model has the final say on every token (its own top choice, or its own sampling distribution), so the drafter changes the speed, not who decides.

4. The tree: spend the 8 rows better

A chain of 7 guesses wastes rows when the drafter is unsure early on: if guess 2 is wrong, guesses 3 to 7 are thrown away. Tree verification uses the same 8 rows but fills them with the drafter's most likely alternatives: when it hesitates between two words, both get a row, and each row only "sees" its own branch. The big model checks the whole tree in one call and keeps the longest correct branch.

Why not a bigger tree? On the Neural Engine, checking 16 or 32 rows cost 26 to 39% or 87 to 116% more per call in a four-layer probe, far more than the extra tokens it would accept. Eight rows is the sweet spot on this chip.

One more trick for long chats: the model keeps a memory of earlier tokens (the KV cache) in sizes of 8K, 16K, 32K, 64K and 96K. Extra "sliced" checks at 24K, 40K, 48K and 56K read only the part of that memory actually in use: +3.4% over a 19-turn coding session, with identical answers.

6. What did not work

  • Bigger trees (16 or 32 rows): the Neural Engine's DeltaNet layers get much slower with more rows.
  • Drafting ahead while the big model checks: the drafter needs the big model's internal features of the tokens it just confirmed, and they do not exist yet (in replay, 48 to 63% fewer tokens kept per check).
  • Running the drafter on the GPU next to the check: both share the same memory bandwidth and slow each other down.
  • Smarter scoring of the tree from the same guesses: even the best possible 7 nodes from the same guesses would add only 8.6 to 10.2%, and every cheap rescoring we tried lost a little. Bigger gains need a better drafter.

7. The fine print

  • This is research, not a release. The GPU reads the weights from macOS's cache of compiled Neural Engine programs, which needs System Integrity Protection turned off and a one-time read permission. Use a dedicated research Mac.
  • Measured on one M6 with 32 GB and macOS 27.3, one model and one drafter. Your numbers will vary with the text.
