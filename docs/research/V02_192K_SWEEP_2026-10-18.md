# Release 0.2 at 192K on the M6: prefill and decode by context and content type (18 Oct 2026)

Release 0.2 weights (`release_vq3pA_mixh_s600_k1_mat`) in a 192K Core AI build for the M6, served with the iPhone
all-3-bit body-only DFlash2 drafter (drafting through the target's head). Measured from 1K to 195K tokens of
context, five kinds of output, four drafters. Two builds:

| Build | Prefill entries | Ladder | KV cache | Tiles (verify / prefill) |
| --- | --- | --- | --- | --- |
| `coreai_v02_m6_p32_192k96` (morning) | 32 rows everywhere | 8K, 16K, 32K, 64K, 96K, 128K, 192K | kv8 | 2048 (4096 at 192K) / 8192 |
| `coreai_v02_m6_mixed_192k96` (served since 20:17) | 64 rows for 8K to 96K, 32 rows for 128K and 192K | same | kv8 | 2048 (4096 at 192K) / 4096 (8192 for the 32-row entries) |

Both use the published C2T attention (INT8 scores, FP8 softmax and PV probabilities, transposed keys) and bonded
compile mode 2. Decode was swept on the morning build; the mixed build changes only the prefill entries (its verify
calls measure the same within 2% at every entry, and a 1K and 32K decode check gave the same verify times and decode
in the same range).

## Drafters

The four drafters on the same model states (50 paired context and task cases; the 160K step is left out because
the system paged right after the 128K to 192K switch):

| Drafter | Neural Engine | Speed (tok/s) vs A | Tokens per verify vs A | Draft call |
| --- | ---: | ---: | ---: | ---: |
| A: LUT4 with its own head copy (published v0.2) | +1.60 GB | 1.000 | 1.000 | 16.5 ms |
| B: the same LUT4 body, target's head | +0.97 GB | 1.003 | 1.005 | 17.2 ms |
| C: all 3-bit body (iPhone) | +0.74 GB | 1.010 | 1.002 | 15.7 ms |
| D: gate/up 2-bit body (iPhone) | +0.63 GB | 1.008 | 0.989 | 14.9 ms |

All four decode at the same speed within 1%; D accepts about 6% fewer prose tokens. C saves 0.86 GB against A and
is the served drafter. B matching A shows that drafting through the target's head costs nothing, so the body-only
drafters need no rebuild for release 0.2 (the head's norm gain is the checkpoint's, unchanged by QAT).

Greedy outputs are not always identical across drafters: A and B (same body) matched token for token in most cases,
C and D diverged from them after a median of about 90 tokens (prose after 20 to 48, JSON never). Verification keeps
each output a greedy decode of the target, but the target's FP16 numerics depend slightly on how accepted runs
split the verify blocks, which changes near-tied choices. Not yet checked against plain decoding.

## Findings and open items

1. **64-row prefill below 128K.** A chunk's scratch is about rows x largest context (the attention scores), so
   64-row entries up to 96K fit inside the scratch the 32-row 192K entries already need: +8 to 13 MB of scratch per
   chunk, plus 31 to 48 MB of weights that the compiler duplicates for 64-row entries. 64 rows at every entry
   doubles the scratch instead (178 to 354 MB per chunk, +2.8 GB) and does not fit next to a 192K cache. Builder:
   `TPS=64 TPS_LONG=32 PREFILL_LONG_FROM=98304 ATT_BLOCK_PREFILL=4096 ATT_BLOCK_PREFILL_LONG=8192`; the manifest records
   the rows per context (`ptp`) and the runtime prefills each entry with its own rows, also across entry switches.
2. **Still below the 64K build.** Its 64-row 8K call takes about 12.6 ms per chunk; this build's takes 14.9 ms with
   real data (the same when a chunk runs alone, so chunks do not slow each other). Suspects: INT8 keys with the FP8
   attention forms (every call dequantizes the entry's whole key cache to FP16 before the score tiles), or programs
   sized for 192K. An October A/B found INT8 keys within 2% of FP16 keys, but before the FP8 forms and transposed
   keys. Planned: a one-chunk A/B with dense inputs (`m6_chunk_ab.py`) over INT8 / FP16 keys and 64K / 192K ladders.
3. **The 192K entry** prefills at 52 to 62 tok/s. A call covers the entry's whole capacity (516 against 336 ms for
   the 128K entry's, in line with 1.5 times the keys), so a prompt just past 128K pays for 192K from there on. A 160K
   entry would keep 128K to 160K prompts out of it.
4. **The 128K to 192K switch** holds both KV caches (+4.3 GB). With the largest drafter loaded, verify calls ran at
   1.1 s instead of 0.2 s for 4 minutes after it. Moving the KV one layer at a time would remove the transient.
5. **Timing with zero inputs** (`neural_mem.py`) is about 15% optimistic against real data (12.75 against 14.9 ms
   per chunk); compare builds with dense inputs.

## Method

One in-process harness reusing the server's `Engine` (prefill, speculative cycles, sampling and statistics as
served). One context of 196,620 tokens, 40 repository source files alternating with 40 cleaned WikiText-2
articles, with six recall codes planted at depths 0 to 185K, prefilled once in 4096-token slices (each timed). At
each size the model state is snapshotted; every drafter and task run restores it, rebuilds the drafter's 2,048-slot
ring from the saved target features of the last 2,056 positions (the state after ingesting the prompt) and decodes
256 tokens (recall: 48, greedy). Context sizes stop short of each entry's capacity so that the task message and the
output stay in the entry the label names. Per-entry rates: a few timed prefill and verify calls in each entry at a
short position; they reproduced the measured prefill of the growing context within 4.3% on both builds. Raw
data: `runs.jsonl` (with every generated text), `prefill.jsonl`, `mem.jsonl`, `needle.jsonl` of the run.
